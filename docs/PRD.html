제품 요구사항 정의서

K콘텐츠로 관심을 갖게 된 동네에서, 외국인이 자신의 취향에 맞는 소상공인 메뉴와 가게 이야기를 찾는다.

제품·디자인·프론트엔드·백엔드·AI·데이터 담당자를 위한 구현 전 기준 문서다. 요구사항은 제안된 제품 계약이며, 구현 완료 보고가 아니다.

1. 문서 기준과 제품 정의

확정한 방향과 아직 가정인 항목

구분내용문서에서의 취급
사용자가 확정한 방향소상공인과 외국인을 연결한다. 상인 및 상인회가 제공한 식당·메뉴 정보로 취향과 이동 조건을 반영한다. 프론트는 React, 백엔드는 Spring을 사용한다.제품과 기술 선택의 기준이다.
검토 후 채택한 제안검증된 작품·촬영 지역 목록, 직접 지역 선택, 상인 확인 정보, 메뉴 단위 추천, 다국어 소개, 한국어 주문 카드와 게시 검수를 MVP로 묶는다.팀 검토용 기본안이다. 요구사항 ID로 변경을 추적한다.
설계 가정시범 지역 한 곳, 영어 방문자 화면, 한국어 상인 화면, 운영자가 검수하는 게시 방식이다.실제 데이터 확보와 팀 역할에 따라 조정한다. 실제 제휴나 검증 완료를 뜻하지 않는다.
현재 확인한 코드원격 Front는 JavaScript, React, react-scripts다. hack은 Spring Boot 4.1.2, Java 17과 WebMVC starter다. 프론트에 localhost:8080 프록시 설정이 있다.설정 파일을 읽은 사실이다. 앱 실행, 라이브러리 조합과 기능 동작은 검증하지 않았다.
아직 정하지 않은 항목최종 서비스명, 실제 작품과 가게, LLM 모델, DB 배포, 도보 제공자, 인증 방식, TypeScript 및 Vite 전환이다.각 담당자와 출시 조건을 15절에 기록한다.

해결할 문제

외국인은 한국어 메뉴 이름만으로 맛과 식감을 예상하기 어렵다. 검색에 잘 드러나지 않는 가게는 해외 방문자에게 메뉴를 설명할 자료가 부족하다. 일반적인 추천 문장만으로는 어떤 메뉴가 예산과 재료 조건을 충족하는지, 누가 그 정보를 확인했는지 알기 어렵다.

이 서비스는 직접 수집한 메뉴 정보와 확인 기록을 축적한다. K콘텐츠는 동네를 고르는 출발점이며, 추천의 대상은 그 주변에서 실제로 판매하는 메뉴다. 실제 촬영 가게가 아닌 주변 가게를 작품에 나온 가게로 표시하지 않는다.

한 줄 제품 정의

외국인이 작품의 촬영 지역 또는 원하는 지역을 고르고 취향을 입력하면, 상인이 확인한 소상공인 메뉴를 추천받고 위치·가격·재료 정보와 가게 이야기를 확인하는 웹 서비스다.

차별화는 특정 LLM보다 성능이 높다는 주장에 두지 않는다. 가게가 제공한 원본, 메뉴별 구조화 정보, 확인일, 수정 과정과 지역 관계를 서비스 안에 유지한다는 점에 둔다.

2. 사용자와 성공 기준

사용자하려는 일완료 상태
외국인 방문자익숙하지 않은 동네에서 취향과 예산에 맞는 메뉴를 찾고, 주문할 내용을 이해한다.메뉴 근거·위치·가격을 확인하고 한국어 주문 카드를 열거나 주소를 복사한다.
소상공인한국어로 가게와 메뉴를 등록하고, AI가 만든 태그와 번역을 검토한다.필수 정보와 공개 범위를 확인하고 검수를 요청한다. 게시 상태와 수정 사유를 안다.
운영자·상인회 담당자확보한 자료의 출처와 관리 권한을 확인하고, 잘못된 정보가 공개되지 않게 한다.자료를 비공개 초안으로 가져오고, 검수를 거쳐 게시하거나 수정을 요청한다.

제품 목표와 측정 계획

아래 수치는 제안된 검증 목표다. 사용자 조사 결과나 서비스 실측 성과가 아니다. 표본과 조건을 함께 보고하고, 실제 검증 전에는 목표 달성을 주장하지 않는다.

목표지표와 제안 기준측정 방법
스스로 메뉴를 고른다대표 과제의 참가자 80% 이상이 진행자의 도움 없이 메뉴 상세에 도달한다.외국어 사용자 대상 소규모 사용성 평가. 참가자 수, 언어, 실패 지점을 함께 기록한다.
정보를 잘못 확정하지 않는다필수 조건 위반, 미확인 식이 정보의 적합 판정, 미게시 데이터 노출은 검증 세트에서 0건이다.고정된 정상·경계·오류 데이터로 서버와 화면 결과를 비교한다.
등록을 끝낼 수 있다상인 역할의 참가자 80% 이상이 메뉴 한 개를 초안 저장하고 검수 요청한다.누락·AI 실패 상황이 포함된 등록 과제를 수행한다. 입력 부담과 수정 횟수를 관찰한다.
느린 요청을 이해한다처리 시작 상태는 즉시 표시한다. AI 해석은 8초를 초기 타임아웃 설정안으로 두고 수동 입력으로 복구한다.모델 선택 뒤 지연시간 분포와 실패율을 측정해 설정을 조정한다. 현재 수치는 실측이 아니다.

검색 완료, 상세 열기, 주문 카드 열기, 초안 저장, 제출, 승인 같은 최소 이벤트를 집계한다. 원문 검색 문장과 정확한 위치, 식이 조건을 분석 이벤트에 기본 포함하지 않는다. 서비스 이용과 무관한 회원가입 전환은 초기 핵심 지표로 삼지 않는다.

3. MVP 범위

우선순위포함 기능출시 또는 시연 조건
P0 핵심직접 지역 선택, 검증된 작품별 장소 진입, 자유 문장과 선택식 취향 입력, AI 해석 확인, 메뉴 단위 추천, 가격·맵기·재료 필수 필터.실제 작품 연결에는 출처가 필요하다. 데이터가 없으면 가상 시연과 실제 서비스를 구분한다.
P0 방문지도 핀과 목록 연결, 메뉴·가게 상세, 확인 상태와 원문·번역, 한국어 주문 카드, 주소 확인.지도 장애에도 목록을 제공한다. 주문 카드는 주문 전송이나 결제를 하지 않는다.
P0 등록·운영상인 수동 등록, AI 태그·번역 초안, 초안 저장, 공개 미리보기, 검수 요청, 운영자 승인·수정 요청, 즉시 품절, 단체 JSON의 검증·초안 가져오기.관리자 역할과 가게 관리 권한을 서버가 검사한다. 검수 전 자료는 공개하지 않는다.
조건부 P0 동선출발점·목적지·최대 도보시간, 실제 보행 소요시간과 목적지까지 추가 우회 시간 반영.도보 API 및 지도와 경로 표시 조건을 확정하고 실제 데이터로 검증해야 활성화한다. 미충족 상태는 동선 추천 완료가 아니다.
P1 확장메뉴판 사진 추출, 추가 언어, 여러 가게 코스, 동의 기반 취향 저장, 검증된 역사문화 자료, 벡터 검색.P0 흐름을 먼저 검증한 후 추가한다. 학습 데이터나 별도 벡터 DB를 초기 필수로 두지 않는다.
이번 범위 밖캡처만으로 촬영지 자동 확정, 예약·결제, 실시간 대기·혼잡 예측, 리뷰 플랫폼, 식이 인증, 근거 없는 상인 이력 생성.화면에 준비된 실제 기능처럼 표시하지 않는다.

지도와 직선거리만 연결한 상태에서는 가까운 위치 탐색까지 시연한다. 원래 요구한 동선 고려는 별도 게이트로 남겨 팀이 구현 상태를 판단할 수 있게 한다. 도보 정보가 없으면 목적지와 최대 도보시간 입력을 비활성화하고 이유를 알린다.

4. 핵심 사용자 흐름

외국인 방문자

  1. S01에서 영어 화면으로 작품의 지역 또는 직접 지역을 선택한다. 현재 위치는 선택 사항이다.
  2. 먹고 싶은 음식을 문장으로 적거나 맛·식감 버튼을 선택한다. 예산과 제외 재료는 추가 조건에서 입력한다.
  3. AI가 해석한 필수 조건과 선호 조건을 확인한다. 모호한 항목을 직접 수정하고 추천을 요청한다.
  4. S02에서 메뉴별 근거를 비교한다. 목록과 지도를 전환해도 같은 식당과 검색 조건을 유지한다.
  5. S03에서 가격 단위, 재료 확인 상태, 가게 이야기와 방문 정보를 확인한다.
  6. S04에서 한국어 메뉴명·수량과 상인이 허용한 옵션을 확인해 가게에 보여준다. 메뉴 상세로 돌아갈 수 있다.

상인과 운영자

  1. 인증된 상인은 S05에서 본인 가게의 초안, 검수 중, 게시, 수정 요청 상태를 확인한다.
  2. S06에 이름·주소·점포 위치·운영 정보·가게 이야기를 입력한다. 일부 항목이 비어 있어도 초안 저장이 가능하다.
  3. S07에 메뉴명·가격·판매 단위·맛·식감·재료를 입력한다. AI 제안을 수정하고 확인한다.
  4. S08에서 외국인 공개 미리보기와 원본을 비교한다. 공개 동의와 필수 확인을 끝내면 검수를 요청한다.
  5. 운영자는 S09에서 출처·관리 권한·공개 범위·필수값을 검사하고 게시하거나 구체적인 수정 사유를 남긴다.
  6. 상인은 게시 후 판매 상태를 즉시 품절로 변경할 수 있다. 가격·재료·이야기 수정은 새 버전으로 검수한다.

단체 자료는 운영자가 같은 식당·메뉴 계약으로 가져온다. 상인회 전용 앱을 별도로 만들지 않는다. 기존 가게와 일치할 수 있는 자료는 중복 후보로 표시하고 자동 덮어쓰지 않는다.

5. 기능 요구사항과 수용 기준

FR은 기능 요구사항, AC는 이를 검증하는 수용 기준이다. 각 AC는 제품 구현을 확인할 때 사용한다. 와이어프레임만으로 서버 권한이나 외부 API의 정확성을 검증했다고 판단하지 않는다.

FR-01 지역과 작품 선택

지역은 필수이며 작품은 선택이다. 확인 출처가 있는 작품·촬영 장소 관계만 탐색 목록에 게시한다. 주변 가게에 실제 촬영 가게라는 배지를 자동 부여하지 않는다.

  • AC-01. 위치 권한을 거부하고 작품을 선택하지 않아도 수동 지역 선택으로 추천 요청을 만들 수 있다.
  • AC-02. 출처 또는 확인일이 없는 작품·장소 연결은 검증된 목록에 나타나지 않는다. 가상 시연 자료에는 샘플 표시가 붙는다.

FR-02 취향 구조화와 확인

다국어 문장을 지역·언어·필수 조건·선호 조건으로 변환한다. 해석 결과를 요청 전에 보여준다. 사용자가 확인한 구조화 조건이 검색 계약이며 원문은 서버의 임의 추정으로 조건을 추가하는 근거가 아니다.

  • AC-03. “not spicy, crispy, under 10,000 won” 예시에서 맵기 상한과 예산은 필수, 바삭함은 선호로 표시되며 사용자가 바꿀 수 있다.
  • AC-04. 모호한 문장이나 AI 실패 시 원문을 보존한다. 선택식 필터로 동일한 추천 API를 이용할 수 있다.

FR-03 메뉴 단위 추천과 필수 필터

게시된 식당의 판매 중인 게시 메뉴만 후보로 삼는다. 필수 조건을 먼저 검사한 뒤 취향 점수와 사용 가능한 위치 정보로 정렬한다. 식당 하나의 특정 메뉴가 적합하다는 이유로 다른 메뉴도 적합하다고 표시하지 않는다.

  • AC-05. 예산 초과, 맵기 상한 초과, 맵기 미확인, 제외 재료 포함 메뉴는 해당 엄격 조건을 통과하지 못한다. 엄격한 재료 제외에서 확인 범위가 불완전한 메뉴도 제외된다.
  • AC-06. 결과가 0건이면 적용한 필수 조건과 정보 부족을 구분해 보여준다. 사용자가 직접 변경하기 전까지 조건을 완화하지 않는다.

FR-04 지도와 목록 연결

식당 좌표를 네이버 지도 위에 표시한다. 동일 식당의 여러 메뉴는 핀 하나에 묶는다. 목록의 추천 단위는 메뉴이고 핀의 위치 단위는 식당이다.

  • AC-07. 메뉴 선택 시 같은 restaurantId의 핀이 강조된다. 핀 선택 시 그 식당의 추천 메뉴 목록이 표시된다.
  • AC-08. 모바일에서 목록·지도 전환 후 선택과 조건이 유지된다. 지도 실패 시 목록, 주소와 재시도가 남는다.

FR-05 도보 동선 반영 · 조건부 출시

도보 제공자가 준비되면 출발점에서 가게까지의 보행 시간을 계산한다. 목적지가 있을 때는 출발점→가게→목적지와 출발점→목적지의 차이를 추가 우회 시간으로 계산한다. 여러 가게 방문 최적화는 P1이다.

  • AC-09. 미연동 또는 실패 상태에서 목적지·도보 제한 입력은 비활성화하거나 해당 요청을 명확히 거부한다. 응답의 walkingMinutes와 detourMinutes는 null이며 시간 숫자를 추정하지 않는다.
  • AC-10. 활성화 전 실제 보행 API 응답으로 최대 도보 제한과 우회 정렬을 검증한다. 경로 제공자·산출 시각·단위를 표시하고 직선거리를 도보거리로 재명명하지 않는다.

FR-06 메뉴 상세와 상인 이야기

메뉴명·가격·단위·맛·식감·등록 재료·미확인 정보·확인일을 먼저 보여준다. 가게 이야기와 문화 설명에는 원본 및 출처를 연결한다. 번역은 원본과 구분한다.

  • AC-11. 목록·상세·상인 미리보기에서 같은 게시 버전의 가격, 확인 상태와 확인일을 표시한다.
  • AC-12. 원문이 없는 역사와 가게 이력을 AI가 추가하지 않는다. 재료 미확인 메뉴에 알레르기 안전·비건·할랄 적합 보장 배지를 표시하지 않는다.

FR-07 한국어 주문 카드

선택한 메뉴의 한국어 이름·수량·가격 단위를 보여준다. 조리 변경은 상인이 가능하다고 등록한 옵션만 고를 수 있다. 화면 제시용이며 가게의 주문 접수와 결제를 의미하지 않는다.

  • AC-13. 수량은 1 이상의 정수이며 메뉴명과 수량이 큰 글씨로 표시된다. 주문 카드에서 뒤로 가면 선택 메뉴가 유지된다.
  • AC-14. 허용 옵션이 없는 메뉴에는 임의의 “재료 빼기” 선택지를 만들지 않는다. 허용 옵션을 선택해도 수용 여부는 현장에서 확인한다는 문구를 표시한다.

FR-08 식당·메뉴 등록과 AI 초안

상인은 한국어 원본을 수동 입력한다. AI는 원본에서 태그와 번역 초안을 만든다. 사진에서 가격·재료를 추출하는 기능은 후순위다. 미완성 정보는 초안으로 저장할 수 있다.

  • AC-15. 이름·가격·판매 단위·위치 등의 필수 게시값이 누락돼도 초안은 저장한다. 검수 요청에서는 누락 요약과 필드 오류를 표시한다.
  • AC-16. AI가 만든 필드는 AI 초안으로 표시된다. 상인이 확인하지 않은 사실을 상인 확인 정보로 공개하지 않는다. AI 실패에도 수동 입력은 작동한다.

FR-09 게시 검수와 소유권

가게 관리 권한을 가진 상인은 초안을 수정하고 검수를 요청한다. 관리자만 게시 승인과 수정 요청을 처리한다. 상인이 본인 판매 메뉴를 즉시 품절로 바꾸는 권한은 내용 검수와 분리한다.

  • AC-17. 다른 상인의 식당 ID로 수정·제출하면 서버가 403을 반환한다. 상인 계정의 게시 승인 요청도 거부한다. 공개 조회는 게시 버전만 반환한다.
  • AC-18. 새 수정안 검수 중에는 기존 게시 버전을 유지한다. 품절 처리한 메뉴는 다음 추천에서 제외한다. 수정 요청 시 사유를 필수로 기록한다.

FR-10 단체 JSON 검증과 초안 가져오기

운영자는 상인회 등에서 받은 자료의 출처·게시 동의·가게 관리 관계를 기록한다. JSON 검증 결과를 확인한 뒤 비공개 초안으로 가져온다. 기존 데이터를 이름만으로 자동 덮어쓰지 않는다.

  • AC-19. 잘못된 가격·좌표·필수 이름이 있으면 행 번호와 필드 경로를 반환하고 실제 가져오기를 실행하지 않는다. 검증 성공 자체는 게시가 아니다.
  • AC-20. 같은 importId를 재시도해도 초안이 중복 생성되지 않는다. 기존 가게 중복 후보와 동의 미확인 항목은 검수 대기로 남는다.

FR-11 다국어와 데이터 관리

MVP 방문자 화면은 영어로 제공한다. 추가 언어 선택은 P1이며 한국어 원문은 상세에서 확인한다. 한국어 원본은 보존한다. 공개 연락처와 비공개 관리자 계정을 다른 응답으로 관리한다. 정확한 위치와 식이 입력은 검색 세션 중심으로 처리한다.

  • AC-21. 번역이 없거나 오래된 경우 원문과 번역 상태를 표시한다. 원본 변경 시 관련 번역과 태그의 재확인 상태가 갱신된다.
  • AC-22. 공개 API 응답에 ownerId·로그인 이메일·내부 검수 메모를 포함하지 않는다. 기본 분석 이벤트에 검색 원문·정확한 위치·식이 제외 재료를 넣지 않는다.

FR-12 장애와 느린 응답의 대체 경로

AI·지도·경로·저장 실패를 구분한다. 처리 상태, 재시도와 수동 대안을 제공한다. 요청 순서가 바뀌면 이전 검색 결과가 최신 조건을 덮지 않도록 한다.

  • AC-23. AI와 지도를 각각 실패시켜도 선택식 검색과 목록 조회가 가능하다. 최신 requestId의 결과만 화면에 적용한다.
  • AC-24. 저장 실패 시 입력값을 보존하고 “저장됨”을 표시하지 않는다. 재시도 중 중복 제출을 막고, 성공 응답 뒤에만 저장·제출 완료를 표시한다.

공통 UI 규칙

모바일에서는 결과 목록을 기본으로 두고 지도 보기로 전환한다. 데스크톱에서는 목록과 지도를 나란히 배치한다. 상세에서 돌아오면 검색 조건과 선택 메뉴를 보존한다. 상인 폼은 모바일에서 한 컬럼, 넓은 화면에서 입력과 미리보기를 분리한다.

추천 행에는 음식 이름, 가격·단위, 맞는 이유, 정보 확인 상태를 표시한다. 별점·후기 수·인기 순위는 수집 범위가 아니므로 자리만 채우기 위해 만들지 않는다. 사진이 없으면 “사진 준비 중”을 표시하며 AI 이미지를 실제 음식 사진으로 위장하지 않는다.

7.4 공통 값과 단위

금액은 원화 정수다. 환율 변환은 MVP 범위 밖이다. 화면에는 8,000원과 1인분을 함께 표시한다. 좌표 필드는 latitude와 longitude를 명시하고 입력 순서에 의존하지 않는다. latitude는 -90~90, longitude는 -180~180 범위를 검사한다. 선택 지역 밖의 좌표는 자동 게시하지 않고 위치 확인 대상으로 돌린다.

시간은 저장 시 시간대가 있는 ISO 8601 형식, 화면에서는 Asia/Seoul 기준으로 표시한다. 날짜만 확보한 확인 기록은 날짜 정밀도를 유지하고 확인 시각을 만들어 넣지 않는다. 영업시간에는 요일별 구간·익일 종료·휴무를 표현할 수 있어야 한다.

8. 게시 상태와 변경 정책

원본·확인·게시를 별도로 관리한다

등록 상태는 문서 전체의 공개 여부이고, 확인 상태는 각 필드의 출처와 검토 상태다. AI 초안이라는 이유만으로 전체 등록을 막을 필요는 없지만, 사실 확인이 필요한 필드를 확인한 것처럼 게시해서는 안 된다. 상인 확인과 운영자 게시 승인도 다른 행동이다.

draft → pending_review → published
                    ↘ changes_requested → draft → pending_review
published → 새 draft revision → pending_review → 새 published revision

판매 상태는 별도: available ↔ sold_out → discontinued
필드 확인은 별도: unknown | ai_draft | merchant_confirmed | operator_confirmed
번역 상태는 별도: missing | ai_draft | reviewed | needs_refresh

9. AI 처리와 추천 규칙

AI가 맡는 일

AI는 사용자 문장을 제한된 검색 스키마로 변환하고, 상인의 원본 설명에서 태그와 다국어 설명의 초안을 만든다. 추천 이유는 실제로 검색된 메뉴의 근거 필드만 이용해 작성한다. AI가 새로운 가게 ID·가격·재료·역사·이동 시간을 만들어 결과에 넣지 않는다.

서버가 맡는 일

  1. 입력값과 AI 출력을 스키마·허용값·길이·숫자 범위로 검증한다.
  2. 사용자가 확인한 필수 조건을 고정한다. 지역·게시·판매 상태를 검사한다.
  3. 가격·맵기·재료 조건을 통과한 메뉴만 후보로 만든다. 알 수 없는 값은 엄격 조건을 통과시키지 않는다.
  4. 선호하는 맛과 식감의 일치를 점수로 계산한다. 초기 가중치는 설정값으로 두고 평가 세트에서 조정한다.
  5. 출발 위치가 있으면 직선거리를 명확히 표시해 정렬하거나, 준비된 도보 API로 실제 시간을 계산한다.
  6. 결과 ID·점수 근거·미확인 필드·경로 상태를 반환한다. LLM은 이 후보 집합 안에서 설명한다.

예산이나 제외 재료를 취향 점수로 상쇄하지 않는다. 추천 점수는 만족 확률이 아니므로 “취향 98% 일치” 같은 수치를 사용자에게 만들지 않는다. 표현이 복잡해져 의미 검색이 필요할 때만 임베딩을 추가한다. 벡터 검색 결과에도 같은 필수 필터를 적용한다.

식이 조건의 경계

“돼지고기를 피하고 싶다”는 재료 제외와 “할랄 인증 음식”은 같은 조건이 아니다. “고기 없음”만으로 채식 또는 비건 적합을 확정하지 않는다. MVP는 확인된 재료 정보와 부족한 부분을 제공한다. 식이 인증이 필요한 요청은 제공 범위를 설명하고 확인된 인증 자료가 없는 가게에 인증 배지를 붙이지 않는다.

자료가 불완전한 메뉴는 정보 부족으로 집계하되 적합 추천 카드 사이에 넣지 않는다. 사용자가 제외 조건을 바꿀 때는 해제된 필수 조건을 명확히 보여준다. 정보가 부족해서 추천이 적어진 사실을 숨기지 않는다.

AI 출력 검증과 실패 대안

허용된 태그 밖의 값, 존재하지 않는 ID, 가격 문자열, JSON 파싱 실패는 검증 오류로 처리한다. 정해진 횟수의 재시도 후 수동 입력을 제공한다. 번역 실패 시 한국어 원본과 “번역 준비 중”을 표시한다. 사용자 문장과 상인 소개에 포함된 명령은 데이터로 처리하며 서버의 시스템 규칙과 권한을 바꾸지 못한다.

  1. 데이터 계약과 샘플 세트를 확정한다. 식당·메뉴·확인 상태·게시 상태를 구분하고, 실제 자료 출처를 확보한다.
  2. Spring의 등록·검증·초안·조회 API와 DB 관계를 구현한다. 공개 API가 게시본만 반환하는지 확인한다.
  3. React에서 지역·선택식 취향·추천 목록·상세 흐름을 연결한다. AI가 없어도 핵심 검색이 동작하게 한다.

  5. 네이버 지도와 식당 핀을 연결한다. 동일 식당의 여러 메뉴와 지도 장애를 검증한다.
  6. 상인 미리보기·제출·운영자 검수·즉시 품절을 연결한다. 단체 자료의 검증과 가져오기를 확인한다.
  7. 도보 제공자와 표시 조건을 확정하면 FR-05를 별도 게이트로 검증한다. 준비되지 않으면 동선 미제공 상태로 명시한다.
  8. 모바일 사용성·필수 조건·권한·외부 장애를 최종 확인하고, 실제와 샘플을 구분한 시연을 준비한다.

대표 시연 시나리오

첫 시연은 작품 목록에서 지역을 고르는 방문자다. “안 맵고 바삭하며 1만 원 이하”를 입력하고, 필수 조건과 선호를 확인한다. 결과에서 메뉴와 핀을 연결하고, 상세의 재료 미확인·확인일·상인 이야기를 보여준다. 한국어 주문 카드를 연다.

두 번째 시연은 상인의 등록이다. 가게 정보와 메뉴를 입력하고 AI 초안을 수정한다. 빠진 가격이 있으면 초안은 저장되지만 제출은 막히는 것을 보여준다. 필수 항목을 채운 뒤 검수를 요청하고, 운영자가 승인하면 공개 버전이 생긴다. 품절 처리는 별도로 즉시 반영한다.

세 번째 시연은 실패 상황이다. 위치 거부 후 직접 지역 선택, AI 실패 후 선택식 입력, 엄격 조건으로 0건, 도보 미연결 상태를 차례로 보여준다. 실패를 숨기기 위해 가짜 결과나 시간을 만들지 않는다.

노션에는 2026-11-06 09:00 제출 일정이 기재되어 있다. 이 문서는 그 일정을 독립적으로 확인하거나 사용자에게 확정받지 않았다. 일정·담당·실제 데이터 확보 상태는 팀이 확인할 운영 항목이다.

pstack Arena에서 두 독립 후보를 비교했다. 지역과 취향을 함께 입력하고 결과에서 조건을 조정하는 후보 B를 기본으로 선택했다. 후보 A의 추천 전 해석 확인과 게시 이후 즉시 품절 처리를 통합했다. 별도 운영자 검수 화면을 유지해 상인 미리보기와 승인 권한을 분리했다.

Experience First에 따라 캡처 자동 인식보다 직접 지역 탐색·확인 가능한 추천·실패 대안을 우선했다. Technical Writing과 Unslop은 구현 사실·가정·제안을 구분하고 짧고 구체적인 요구사항을 쓰는 기준으로 적용했다. 독립 에이전트는 같은 모델 설정을 상속했으며 모델 다양성 검토를 수행했다고 주장하지 않는다.

동네 한 끼는 가칭이다. 이 문서는 PRD 초안 v0.1이며 앱 소스 수정·배포·실제 식당 데이터 확보를 포함하지 않는다. PRD는 저장소 문서로 인계한다. 연결된 와이어프레임의 모든 작품·가게·가격·관계·지도는 설계 검토용 샘플이다.
