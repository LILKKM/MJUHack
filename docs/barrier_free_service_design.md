# 서울 배리어프리 여행 서비스 설계

> 데이터 출처: 한국관광공사 「무장애 여행 정보」 OpenAPI (공공데이터포털)
> 대상 지역: 서울특별시

이 문서는 같은 데이터를 활용하는 두 가지 기능의 구조를 설명한다.

1. **배리어프리 코스 추천**: 이용자 조건을 받아 실제로 이동할 수 있는 여행 코스를 만들어 준다.
2. **챗봇을 통한 주변 정보 습득**: 대화로 주변의 접근 가능한 장소와 시설 정보를 묻고 답한다.

두 기능은 같은 원칙을 따른다.

> **필터링과 계산은 DB/코드에서, 설명과 대화는 LLM에서**

---

## 0. 공통 기반: 데이터 수집 및 전처리 (오프라인, 1회성 + 주기적 동기화)

요청마다 API를 호출하지 않는다. 데이터를 미리 받아 자체 DB에 저장해 두고 쓴다.

### 0-1. 왜 미리 받아두는가

| 항목 | 요청마다 API 호출 | 자체 DB 구축 |
|---|---|---|
| 트래픽 제한 (개발계정 1,000건/일) | 쉽게 초과 | 수집 시에만 사용 |
| 응답 속도 | 느림 (외부 호출 여러 번) | 빠름 (로컬 쿼리) |
| 필터/정렬 자유도 | API 파라미터에 종속 | SQL로 자유롭게 |
| 텍스트 구조화 | 매번 다시 해야 함 | 한 번만 처리 |

> 공공데이터포털의 「열린관광지목록」 CSV는 2022년 1회성 데이터이고 편의시설 상세 항목이 없다. 그래서 반드시 OpenAPI로 수집한다.

### 0-2. 수집 흐름

```
[지역기반 목록 API] ── 서울 지역코드로 전체 장소 목록 수집
        │  (contentId, 이름, 유형, 주소, 좌표 mapx/mapy)
        ▼
[무장애 정보 API] ── contentId별 편의시설 상세 조회
        │  (주차, 접근로, 휠체어, 출입구, 엘리베이터, 화장실,
        │   점자블록, 안내견, 오디오가이드, 수어, 유모차, 수유실 …)
        ▼
[원본 저장] raw_places, raw_barrier_free
```

※ 정확한 엔드포인트명과 파라미터는 활용신청 후 받는 `TourAPI_Guide_(무장애)` 문서에서 확인한다.

### 0-3. 텍스트 구조화 (가장 중요한 전처리)

무장애 항목은 대부분 자유 텍스트다.

```
"장애인 화장실 있음(1층 매표소 옆)"
"경사로 있으나 경사가 다소 급함"
"없음"
```

이 텍스트를 LLM이나 규칙 기반으로 한 번 처리해서 **정형 컬럼**으로 바꾼다.

| 원문 | 변환 값 |
|---|---|
| 있음 / 가능 / 비치 | `1` (있음) |
| 있으나 ~ / 일부 / 문의 | `0.5` (부분) |
| 없음 / 공란 | `0` (없음 또는 정보 없음) |

LLM 호출 비용은 이 단계에서 **한 번만** 든다.

### 0-4. 최종 테이블 예시

```sql
CREATE TABLE places (
    content_id      TEXT PRIMARY KEY,
    name            TEXT,
    category        TEXT,      -- 관광지 / 문화시설 / 음식점 / 숙박 ...
    address         TEXT,
    lat             REAL,
    lng             REAL,
    tel             TEXT,
    -- 지체장애
    parking_ok      REAL,
    route_ok        REAL,      -- 접근로
    wheelchair_ok   REAL,
    entrance_ok     REAL,
    elevator_ok     REAL,
    restroom_ok     REAL,
    -- 시각장애
    braille_ok      REAL,
    guidedog_ok     REAL,
    audioguide_ok   REAL,
    -- 청각장애
    signlang_ok     REAL,
    -- 영유아·고령
    stroller_ok     REAL,
    nursing_ok      REAL,
    -- 원문 보존 (설명 생성/검증용)
    raw_text        TEXT,
    updated_at      TEXT
);
```

### 0-5. 동기화

API에 있는 "무장애 여행정보 동기화 목록" 기능으로 변경된 장소만 주기적으로(예: 주 1회) 다시 받는다.

## 1. 방식 A: 배리어프리 코스 추천

### 1-1. 개요

이용자가 조건을 입력하면, 서비스가 **접근 가능한 장소들을 이동 동선까지 고려해 묶은 코스**를 돌려준다.

### 1-2. 전체 흐름

```
[사용자 입력]
  유형(휠체어/시각/청각/영유아·고령), 출발지, 관심사, 소요 시간
        │
        ▼
[① 후보 필터링]  ── SQL
        │  유형별 필수 조건 + 반경 N km
        ▼
[② 접근성 점수 계산]  ── 코드
        │  유형별 가중치 합산
        ▼
[③ 코스 구성]  ── 코드
        │  앵커 장소 선정 → 근거리 클러스터링 → 식당/휴식처 삽입 → 방문 순서 결정
        ▼
[④ 설명 생성]  ── LLM
        │  최종 코스(장소 3~5곳 + 필요한 필드만)만 전달
        ▼
[결과 출력]  코스 + 장소별 접근성 요약 + "방문 전 확인" 연락처
```

### 1-3. 단계별 상세

#### ① 후보 필터링 (SQL)

유형별 **필수 조건**을 걸고, 출발지 기준 반경으로 거른다.

```sql
-- 휠체어 이용자, 출발지 반경 3km 예시
SELECT *
FROM places
WHERE wheelchair_ok >= 0.5
  AND restroom_ok   >= 0.5
  AND distance_km(lat, lng, :start_lat, :start_lng) <= 3;
```

`distance_km`는 하버사인 공식으로 구현한다. SQLite는 사용자 정의 함수로 등록하고, PostgreSQL은 PostGIS를 쓴다.

#### ② 접근성 점수 (가중치)

| 유형 | 높은 가중치 항목 |
|---|---|
| 휠체어 | 접근로, 출입구, 엘리베이터, 장애인 화장실, 주차 |
| 시각장애 | 점자블록, 안내견 동반, 오디오가이드 |
| 청각장애 | 수어 안내, 자막/영상 안내 |
| 영유아·고령 | 유모차, 수유실, 엘리베이터, 화장실 |

```
score = Σ (항목 가중치 × 항목 값)  +  관심사 일치 보너스
```

#### ③ 코스 구성

1. **앵커 선정**: 점수와 관심사가 높은 관광지·문화시설 2~3곳을 고른다.
2. **클러스터링**: 앵커 주변의 후보를 좌표 기반으로 묶는다. 앵커 사이 거리가 멀면 다른 앵커로 교체한다.
3. **식당/휴식처 삽입**: 동선 중간에 `restroom_ok`가 높은 음식점이나 카페를 넣는다.
4. **순서 결정**: 출발지에서 가까운 순으로 고르는 탐욕(greedy) 방식이면 충분하다.

#### ④ 설명 생성 (LLM)

LLM에는 **최종 코스만** 넘긴다. 전체 데이터를 넘기지 않는다.

```
[System]
너는 배리어프리 여행 가이드다. 주어진 장소 정보 안에서만 설명하고,
주어지지 않은 시설 정보는 추측하지 마라.

[User]
이용자 유형: 휠체어
코스:
1. 국립중앙박물관 - 엘리베이터 O, 장애인화장실 O, 휠체어 대여 O
2. ○○식당 - 출입구 단차 없음, 장애인화장실 O
3. ...
이 코스를 소개하고, 장소별 이용 팁을 알려줘.
```

### 1-4. 한계와 보완

| 한계 | 보완 방법 |
|---|---|
| **장소 사이 이동 경로의 접근성 정보가 없음** | 지하철역 엘리베이터 위치, 저상버스 노선 같은 서울시 공공데이터를 결합한다. 도보 구간에는 최대 거리 상한을 둔다. |
| 자유 텍스트 구조화 오류 | 원문(`raw_text`)을 보존해서 결과 화면에 함께 표시한다. |
| 정보 갱신 시점이 장소마다 다름 | "방문 전 확인 권장" 문구와 연락처를 노출하고, 주기적으로 동기화한다. |

> **차별점**: 단순한 "무장애 장소 목록"이 아니라 "실제로 다닐 수 있는 코스"를 제공한다.

## 2. 방식 B: 챗봇을 통한 주변 정보 습득

### 2-1. 개요

이용자가 자연어로 묻는다. ("근처에 휠체어로 갈 수 있는 식당 있어?", "여기 화장실 쓸 만해?")
챗봇은 **DB를 도구(tool)로 호출**해서 실제 데이터를 근거로 답한다.

### 2-2. 맥락(Context) 유지 원리

LLM API는 **stateless**라서 이전 대화를 기억하지 못한다.
그래서 **서버가 맥락을 저장하고, 매 요청마다 함께 보낸다.**

```
            ┌─────────────── 서버 (세션 ID별 저장) ───────────────┐
            │  ① 대화 기록 (messages)                              │
            │  ② 사용자 상태 (state JSON)                          │
            └─────────────────────────────────────────────────────┘
                     │ 매 요청마다 ①+② 를 함께 전송
                     ▼
                  [LLM API]
```

#### ① 대화 기록

```python
history.append({"role": "user", "content": user_msg})
resp = client.messages.create(
    model=MODEL,
    system=build_system_prompt(state),
    messages=history,
    tools=TOOLS,
)
history.append({"role": "assistant", "content": resp.content})
```

저장소: 서버 메모리(프로토타입) → Redis 또는 DB(실서비스)

#### ② 사용자 상태 (핵심 조건은 대화와 분리)

```json
{
  "user_type": "wheelchair",
  "location": {"lat": 37.5796, "lng": 126.9770},
  "language": "ko",
  "current_course": ["126508", "264337", "1945623"]
}
```

이 상태를 매 요청마다 **시스템 프롬프트에 넣는다.** 대화가 길어져도 핵심 조건이 사라지지 않는다.

#### ③ 긴 대화 처리

- 최근 N턴(예: 10턴)은 원문 그대로 보낸다.
- 그보다 오래된 대화는 짧게 요약해서 한 덩어리로 넣는다.
- 토큰 비용이 줄고, 컨텍스트 한도 문제도 피할 수 있다.

### 2-3. Tool Use (Function Calling)

LLM에 "쓸 수 있는 함수"를 알려주면, LLM이 필요할 때 그 함수를 호출한다.

```python
TOOLS = [
    {
        "name": "search_places",
        "description": "현재 위치 주변에서 조건에 맞는 접근 가능한 장소를 검색한다.",
        "input_schema": {
            "type": "object",
            "properties": {
                "category":  {"type": "string", "description": "관광지/음식점/숙박 등"},
                "radius_km": {"type": "number"},
                "required":  {"type": "array", "items": {"type": "string"},
                              "description": "필수 편의시설 (예: restroom_ok)"}
            },
            "required": ["category"]
        }
    },
    {
        "name": "get_place_detail",
        "description": "특정 장소의 무장애 시설 상세 정보를 조회한다.",
        "input_schema": {
            "type": "object",
            "properties": {"content_id": {"type": "string"}},
            "required": ["content_id"]
        }
    },
    {
        "name": "update_course",
        "description": "현재 코스에서 장소를 추가, 삭제, 교체한다.",
        "input_schema": {
            "type": "object",
            "properties": {
                "action":     {"type": "string", "enum": ["add", "remove", "replace"]},
                "content_id": {"type": "string"},
                "position":   {"type": "integer"}
            },
            "required": ["action"]
        }
    }
]
```

### 2-4. 대화 처리 흐름 예시

```
사용자: 근처에 휠체어로 갈 수 있는 식당 있어?
   │
   ▼
LLM ─▶ tool_use: search_places(category="음식점", radius_km=1,
                               required=["wheelchair_ok","restroom_ok"])
   │      (user_type, location은 state에서 서버가 자동으로 채움)
   ▼
서버 ─▶ SQL 실행 → 상위 5개 결과 반환
   │
   ▼
LLM ─▶ "근처에 이용 가능한 식당이 3곳 있어요. ○○식당은 입구 단차가 없고…"
```

```
사용자: 아까 코스에서 두 번째 장소 빼고 다른 데 넣어줘
   │
   ▼
LLM ─▶ update_course(action="remove", position=2)
     ─▶ search_places(...)  → 대체 후보 검색
     ─▶ update_course(action="add", content_id=..., position=2)
   │
   ▼
서버 ─▶ state.current_course 갱신
```

### 2-5. 환각(없는 장소 지어내기) 방지

- 시스템 프롬프트에 "도구 결과에 없는 장소나 시설은 언급하지 말 것"이라고 명시한다.
- 장소 추천은 반드시 `search_places` 결과 안에서만 하도록 한다.
- 답변에 `content_id`를 포함시켜, 화면에서 지도나 상세 페이지로 연결한다.

## 3. 두 방식의 비교 및 결합

| 구분 | A. 코스 추천 | B. 챗봇 |
|---|---|---|
| 입력 | 폼 (유형, 출발지, 관심사) | 자연어 대화 |
| 출력 | 완성된 코스 1개 이상 | 질문에 대한 답변, 코스 수정 |
| 핵심 로직 | SQL 필터 + 점수 + 동선 알고리즘 | Tool Use + 상태 관리 |
| LLM 역할 | 최종 코스 설명 | 의도 파악, 도구 호출, 답변 생성 |
| 장점 | 결과가 일관적, 비용 낮음 | 유연함, 후속 질문 가능 |

### 결합 방안

```
[A. 코스 추천]으로 첫 코스 생성
        │
        ▼  state.current_course 에 저장
[B. 챗봇]으로 수정·질문
  "두 번째 장소 화장실 어때?"  → get_place_detail
  "점심은 더 가까운 데로"      → search_places + update_course
```

방식 A의 코스 생성 로직을 `recommend_course` 도구로 챗봇에 등록하면, 두 기능을 하나의 대화형 서비스로 합칠 수 있다.

## 4. 기술 스택 (예시)

| 영역 | 프로토타입 | 확장 시 |
|---|---|---|
| 데이터 수집 | Python + requests | 스케줄러 (cron) |
| 저장소 | SQLite | PostgreSQL + PostGIS |
| 대화 상태 | 서버 메모리 dict | Redis |
| 백엔드 | FastAPI | FastAPI |
| LLM | Claude / OpenAI API (Tool Use) | 동일 |
| 지도 | 카카오맵 API | 동일 |

## 5. 구현 순서 제안

1. 공공데이터포털 활용신청 → API 키 발급
2. 서울 데이터 수집 스크립트 작성 → `raw_*` 테이블 저장
3. 무장애 텍스트 구조화 → `places` 테이블 완성
4. **방식 A**: SQL 필터 + 점수 + 동선 로직 → LLM 설명 연결
5. **방식 B**: 상태 관리 + Tool Use 챗봇 구현
6. A를 B의 도구로 통합
7. (확장) 지하철 엘리베이터, 저상버스 데이터 결합으로 이동 구간 접근성 반영
